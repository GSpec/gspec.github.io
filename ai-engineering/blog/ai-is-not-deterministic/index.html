Do we understand that AI is non-deterministic?

The short answer: Most everyday users do not realize it, and even experienced software engineers struggle with the mental shift.

Decades of interacting with technology have trained us to view software as a deterministic system. If you type 2 + 2 into a calculator, run a SQL query, or click a button in an app, you expect the exact same output every single time.

Generative AI breaks this fundamental contract. Understanding why people struggle with this—and why the underlying systems behave this way—requires breaking down the psychological and technical gaps.

How We View AI: The Predictive Text Misconception

Most non-technical users view Generative AI through one of two flawed mental models:

  • The Search Engine Model: They think the AI is retrieving a stored answer from a database. If the answer changes on a second attempt, they assume the AI “found better data” or “corrected itself,” rather than understanding it just generated a new probabilistic path.

  • The Magic Black Box Model: When the AI gives two different answers, users often interpret it as human-like flakiness, indecisiveness, or “hallucination,” without grasping that randomness is an intentional parameter of the math.

Because modern software UI is polished and deterministic, users naturally project that same determinism onto LLMs. When an LLM fails to deliver consistency, users experience it as a defect rather than a core structural property of probabilistic computing.

Why AI is Non-Deterministic (Even at “Temperature = 0”)

Even when people realize AI isn’t a traditional database, they often assume setting the “temperature” parameter (the randomness knob) to 0 will make it 100% deterministic. In reality, non-determinism in modern AI occurs across multiple layers:

A. Token Sampling & Probability Distributions

An LLM doesn’t “know” facts; it calculates the probability of the next word (token) given all previous words.

  • At higher temperatures, it rolls a weighted die to pick from top candidates to foster “creativity.”

  • At $T=0$ (greedy decoding), it always picks the top token. However…

B. Hardware & Floating-Point Variance (The GPU Problem)

Even at $T=0$, modern GPUs run massive matrix multiplications in parallel across thousands of cores. Because floating-point addition in computer hardware is non-associative—meaning $(a + b) + c$ does not always bit-for-bit equal $a + (b + c)$ at extreme decimal precision—the order in which parallel threads finish calculation introduces micro-variations. A shift in the 15th decimal place of a token’s probability score can cause the model to pick a completely different word, swinging the rest of the sentence off in a new direction.

C. Mixture of Experts (MoE) Routing

Models like GPT-4, Gemini, and Claude use MoE architectures, where different “expert” sub-networks handle different tokens. In high-throughput cloud infrastructure, token routing depends on batch composition and thread timing. If another user’s request is processed in the same server batch as yours, it can subtly shift which expert handles your request.

The Expectation Gap Across User Archetypes

User Group Expectation Realization Level Primary Reaction to Variability
General Public Deterministic (Database) Very Low Frustration; loss of trust (“It lied to me,” “It’s broken”).
Business Leaders Deterministic (API / Feature) Moderate Surprise when edge-case testing fails in production.
Software Engineers Deterministic (Logic / Rules) High Structural discomfort; struggle to write tests for non-reproducible outputs.
AI Engineers Probabilistic (Distribution) Complete Treat variability as a feature to be bounded by schemas, guardrails, and validation chains.

Why This Expectation Gap is Dangerous for Software Teams

In fields like fintech, medical software, or legal tech, the expectation of determinism is paramount. When traditional engineers try to build on top of non-deterministic LLMs, they run into three major hurdles:

  • Broken Unit Testing: Traditional unit tests pass or fail based on expected outputs. You cannot write an exact-match unit test for an LLM because identical inputs don’t equal identical outputs.

  • Debugging Phantom Bugs: Finding the root cause of an error becomes probabilistic. If a user gets a bad output, an engineer attempting to reproduce the error in local testing might get a valid response every time.

  • Compliance & Auditability: Regulatory bodies (e.g., FINRA, SEC, HIPAA) require audit trails. Demonstrating why a system made a specific automated decision becomes difficult if the system cannot replay the exact execution path.

The Hybrid Solution

To bridge this gap, modern software architecture uses deterministic wrappers around non-deterministic engines:

[ Unpredictable LLM Output ] ──► [ Schema Validation ] ──► [ Deterministic Business Logic ]

By forcing LLMs to output structured data (like JSON following strict schemas) and passing those payloads into deterministic code (like traditional Python or C++ logic), engineering teams can harness the creative reasoning of AI without giving up the reliability of traditional computing.
